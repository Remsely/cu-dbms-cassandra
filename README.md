# Cassandra: аудит действий пользователя

Сервис записывает действия пользователя (`login`, `purchase`, `view`) и читает его последние события. На стенде работают
три узла Cassandra 5.0.4; для пространства ключей `hw3` задан фактор репликации 3.

## Воспроизведение

Нужны Docker с Compose v2 и Bash. Сценарии пересоздают пространство ключей `hw3` и удаляют его данные.

```bash
docker compose up -d
docker compose run --rm lab reset
docker compose run --rm lab all
bash ops.sh tablestats
bash ops.sh repair
```

`all` последовательно запускает `data`, `compaction`, `bulk` и `consistency`. Перед каждым сценарием пространство ключей
очищается, поэтому после `all` в таблицах остаются данные сценария `consistency`. Чтобы отдельно проверить TTL и
трассировку, выполните:

```bash
docker compose run --rm lab compaction
docker compose run --rm lab shell
```

В открывшемся `cqlsh`:

```sql
TRACING ON;
SELECT event_time, event_type
FROM hw3.user_actions
WHERE user_id = 3001;
EXIT;
```

После этого выполните компакцию и проверку файлов, затем остановите стенд:

```bash
bash ops.sh compact
docker compose run --rm lab metrics
docker compose down
```

Результаты последнего прогона сохранены в [results](results/README.md), скриншоты предыдущего прогона –
в [DEMO.md](DEMO.md). Время выполнения на скриншотах может отличаться от текущих результатов.

## Таблица и модель данных

> Почему партиция по `user_id`?

Лента запрашивается для конкретного пользователя. По `user_id` координатор определяет реплики нужной партиции, поэтому запрос не требует поиска по всему кластеру.

> Зачем обратный порядок кластеризации?

При `event_time DESC` самые новые события находятся в начале партиции. Запрос с `LIMIT N` возвращает последние N событий без дополнительной сортировки.

> Что произойдёт, если у двух событий одного пользователя совпадёт `event_time`?

Их первичный ключ совпадёт, и новая запись может затереть прежнюю. Для аудита это потеря события. Чтобы этого избежать, можно добавить в ключ уникальный `event_id timeuuid`: `PRIMARY KEY (user_id, event_time, event_id)`.

## Вставка и чтение

| Что вставлено | Сколько | Время |
|---|---:|---:|
| События пользователя 1001 (`login`, `purchase`, `view`) | 10 000 | 14,009 с, в среднем 1,401 мс на запись |

Сценарий `bulk` подтвердил количество записей и порядок чтения последних событий.

> Что даёт PreparedStatement?

В `insert_events` запрос подготавливается перед циклом. Затем драйвер передаёт идентификатор запроса и значения параметров, поэтому серверу не нужно заново разбирать текст при каждой вставке. Параметры передаются отдельно от текста запроса.

## Консистентность

Медианы пяти прогонов после прогрева: время записи 1000 событий и чтения 20 последних событий.

| Уровень | Запись, мс | Чтение, мс |
|---|---:|---:|
| ONE | 1222 | 3 |
| QUORUM | 1485 | 7 |

> Что означает формула W + R > N и какие гарантии даёт QUORUM?

`N` – число реплик, `W` – число подтверждений записи, `R` – число ответов при чтении. Если `W + R > N`, среди ответивших при записи и чтении есть хотя бы одна общая реплика.

При `ONE` достаточно одной реплики, при `QUORUM` в нашем кластере из трёх реплик – двух. Запись и чтение с `QUORUM` дают `2 + 2 > 3`: подтверждённая запись будет видна при отсутствии конфликтующей записи с более поздней временной меткой. При `ONE` и для записи, и для чтения пересечение не гарантировано, поэтому чтение может вернуть устаревшие данные.

> Какой уровень консистентности выбрать для ленты событий?

Я бы выбрал `QUORUM` для записи и чтения, чтобы пользователь видел своё действие после подтверждения записи. Цена этого выбора – ожидание двух реплик и недоступность операции, если доступна только одна.

> В чём компромисс сжатия и почему оно выгодно для этого случая?

Сжатие и распаковка требуют времени процессора, но уменьшают объём данных на диске и при чтении с него. В событиях повторяется структура JSON, поэтому они хорошо сжимаются: в этом прогоне таблица с LZ4 заняла на `c1` примерно в 2,3 раза меньше места.

## Bloom-фильтр

| Показатель | Значение |
|---|---:|
| Bloom filter false positives | 0 |
| Bloom filter false ratio | 0,00000 |

> Как работает Bloom-фильтр?

Для каждой SSTable фильтр проверяет, может ли она содержать нужную партицию. При отрицательном ответе поиск в этой SSTable можно пропустить. При положительном ответе поиск нужен: ответ может оказаться ложным, и тогда обращение к диску всё же потребуется.

> Что означают метрики и когда фильтр полезен?

`false positives` – число ложных срабатываний, `false ratio` – их доля. Фильтр особенно полезен при поиске отсутствующих ключей среди множества SSTable: он позволяет не проверять файлы, которые точно не содержат ключ. При попадании в кэш его польза меньше. Нули в нашем прогоне не означают, что ложных срабатываний не бывает.

## Repair

`bash ops.sh repair` завершился успешно; вывод сохранён в [repair.txt](results/repair.txt).

> Что такое anti-entropy и зачем нужен nodetool repair?

Anti-entropy – это сверка разошедшихся реплик вне пути чтения. `nodetool repair` сравнивает Merkle-деревья реплик, находит различающиеся диапазоны и передаёт недостающие изменения.

> Когда нужен repair и что произойдёт без него?

Repair нужен регулярно и после длительного простоя узла, когда hinted handoff уже не может доставить пропущенные записи. Без него реплики расходятся, а чтение может вернуть устаревшие данные. Если недоступный узел пропустил удаление, а остальные реплики уже убрали tombstone, старая запись может снова распространиться по кластеру. Поэтому интервал между repair должен быть меньше `gc_grace_seconds`.

> Чем repair отличается от read repair и hinted handoff?

Read repair исправляет расхождения при чтении только для затронутых данных. Hinted handoff доставляет пропущенные записи после короткого простоя узла. Repair сверяет реплики и для данных, которые никто не читает.

## TTL и компакция

Для `user_actions` настроены `TimeWindowCompactionStrategy` с окном в один день и `default_time_to_live = 2592000` секунд (30 дней). В эксперименте пять записей с TTL 5 секунд были видны до истечения срока; через 8 секунд их не осталось. Результат чтения с tracing и история принудительной компакции сохранены в [tracing.txt](results/tracing.txt) и [compaction.txt](results/compaction.txt).

> Почему TWCS подходит для журнала событий, а STCS подходит хуже?

TWCS группирует SSTable по временным окнам. Если события записаны примерно в одно время и имеют одинаковый TTL, они истекают примерно одновременно. Тогда файл без живых данных можно удалить целиком при соблюдении условий удаления. STCS объединяет SSTable по размеру и может смешивать старые и новые данные, поэтому при очистке такого файла живые записи придётся сохранить и переписать.

> Как TTL связан с gc_grace_seconds?

После истечения TTL запись перестаёт возвращаться при чтении, а информация об истечении учитывается как tombstone. `gc_grace_seconds` задаёт период, в течение которого маркер сохраняется, чтобы дать время на сверку реплик. После этого компакция может удалить его при соблюдении необходимых условий.

> Почему TTL удобнее массового DELETE?

TTL задаётся вместе с записью: не нужно отдельно искать старые события и отправлять массовый `DELETE`. При этом истёкшие данные тоже создают tombstone и требуют обслуживания.
