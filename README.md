# ДЗ_3. Cassandra: сервис аудита действий пользователя

Сервис пишет действия пользователя (`login`, `purchase`, `view`) в таблицу `user_actions` и читает ленту последних событий. Стенд: три узла Cassandra 5.0.4 (`c1`, `c2`, `c3`) в docker, keyspace `hw3`, RF = 3.

## Как воспроизвести

```bash
docker compose up -d
docker compose run --rm lab reset
docker compose run --rm lab all
bash ops.sh tablestats
bash ops.sh repair
bash ops.sh compact
docker compose run --rm lab metrics
docker compose down
```

Результаты в `results/` (`results.json` и выводы nodetool). Скриншоты выполнения разделов: [DEMO.md](DEMO.md).

## 2. Таблица и модель данных

```sql
CREATE TABLE user_actions (
    user_id     int,
    event_time  timestamp,
    event_type  text,
    payload     text,
    PRIMARY KEY (user_id, event_time)
)
WITH CLUSTERING ORDER BY (event_time DESC)
  AND compression = {'class': 'LZ4Compressor'};
```

`user_actions_none`: та же таблица без сжатия, контрольная для раздела 5.

> Почему партиция по `user_id`?

Запрос приложения один: события конкретного пользователя. Хеш `user_id` попадает в один диапазон кольца, то есть на фиксированный набор реплик, и все события пользователя лежат рядом на диске. Время ответа зависит только от размера партиции, а не от размера таблицы.

> Зачем обратный порядок кластеризации?

Строки внутри партиции физически хранятся в порядке кластеризации. С DESC свежие события в начале, поэтому последние N событий это `LIMIT N` без сортировки. С прямым порядком пришлось бы читать те же N строк в обратную сторону, а обратная навигация дороже прямой.

> Что произойдёт при двух событиях одного пользователя с одинаковым `event_time`, почему для аудита это риск и как изменить схему?

Ключ совпадёт, а запись в Cassandra это upsert: второе событие молча перезапишет первое, клиент ошибки не получит. Для аудита это потеря события. Лечение: добавить `event_id timeuuid` в ключ, `PRIMARY KEY (user_id, event_time, event_id)`; timeuuid уникален и монотонен, лента читается так же одним `LIMIT N`.

## 3. Вставка и чтение

| Что вставлено | Сколько | Время |
|---|---|---|
| События пользователя 1001 (login, purchase, view) | 10 000 | 4.626 с (0.46 мс на запись) |

> Что даёт PreparedStatement?

Запрос парсится и компилируется на сервере один раз, дальше по сети уходят только значения с токеном: из 10 000 вставок ни одна не парсится заново. Драйвер проверяет типы при биндинге, значения кодируются отдельно от текста запроса, поэтому инъекции невозможны. Уровень консистентности задаётся на каждом statement, а не на сессии.

## 4. Консистентность: ONE и QUORUM

| Уровень | Запись, мс (серия 1000) | Чтение, мс (20 строк) |
|---|---|---|
| ONE | 458 | 2 |
| QUORUM | 647 | 2 |

> Объясните формулу W + R > N. Что меняется между ONE и QUORUM и какие гарантии даёт QUORUM?

N это число реплик партиции (3), W сколько реплик подтверждают запись, R сколько ответов ждёт чтение. Если W + R > N, множества реплик пересекаются минимум на одной, и чтение обязательно видит последнюю подтверждённую запись. Неравенство строгое: ONE-запись плюс QUORUM-чтение даёт 1 + 2 = 3 = N, пересечения нет. ONE подтверждает запись первой ответившей репликой и читает первый ответ: минимальная латентность, но до полной репликации чтение возвращает старые данные. QUORUM ждёт двух подтверждений; чтение опрашивает все реплики партиции (полный ответ с одной, digest с остальных, при несовпадении read repair) и видит все предыдущие QUORUM-записи. Замер: 647 против 458 мс, +41% за ожидание второй реплики.

> Какой уровень консистентности выбрали бы для ленты событий и почему?

Чтение QUORUM, запись ONE: пользователь читает ленту сразу после действия, запись ведёт фоновый поток, недостающие копии довезут hinted handoff и read repair. Если нужно видеть своё событие немедленно, запись тоже QUORUM: 2 + 2 > 3 закрывает окно, цена +0.19 мс на запись.

## 5. Сжатие

| Таблица | Space used (total) | SSTable count | Compression Ratio |
|---|---|---|---|
| `user_actions` (LZ4) | 34 141 байт | 1 | 0.38464 |
| `user_actions_none` (без сжатия) | 78 276 байт | 1 | -1 |

> В чём компромисс сжатия и почему оно выгодно для этого кейса?

Плата: CPU на компрессию при записи и декомпрессию при чтении. Выигрыш: меньше байт на диске и чтения с него, больше рабочего набора в page cache. Журнал это текстовый JSON с повторяющимися ключами и жмётся хорошо: одинаковые данные сжались в 2.3 раза. Чтение ленты последовательное, декомпрессия LZ4 дешёвая.

## 6. Bloom-фильтр

| Показатель | Значение |
|---|---|
| Bloom filter false positives | 0 |
| Bloom filter false ratio | 0.00000 |

> Что делает bloom-фильтр и почему при обращении к отсутствующему ключу disk lookup не нужен?

Фильтр строится на каждую SSTable по ключам её партиций и держится в памяти. Отрицательный ответ всегда точный, положительный с долей ложных срабатываний (`bloom_filter_fp_chance`, 0.01). Если ключа нет, все фильтры отвечают отрицательно, SSTable не открываются, обращения к диску нет.

> Что означает метрика и когда bloom-фильтр полезен, а когда не важен?

`false positives`: сколько раз фильтр зря ответил положительно и пришлось проверять SSTable. `false ratio`: доля таких случаев от всех проверок. Нули объясняются малым числом SSTable и ключей. Полезен при большом числе SSTable и запросах по несуществующим ключам; не важен, когда ключи почти всегда существуют и кэшируются.

## 7. Repair

`bash ops.sh repair`, вывод в `results/repair.txt`: `Repair completed successfully`.

> Что такое anti-entropy и зачем нужен nodetool repair?

Плановая сверка реплик вне путей записи и чтения: на репликах строятся Merkle-деревья (свёртки хешей данных), сравниваются, расхождения стримятся на отставшую реплику. Закрывает расхождения, которые не поймали read repair и hinted handoff.

> Когда без repair не обойтись и что происходит при долгой работе без него?

После простоя узла дольше `max_hint_window` (3 часа), при замене и добавлении узлов, после restore из бэкапа, и регулярно с интервалом меньше `gc_grace_seconds`, чтобы tombstone-ы доходили до всех реплик. Без него реплики расходятся, чтение при ONE возвращает устаревшие данные, возможно resurrection удалённых строк.

> Чем repair отличается от read repair и hinted handoff?

Read repair встроен в чтение с уровнем выше ONE и чинит только читаемые ключи. Hinted handoff закрывает простои до 3 часов и гибнет вместе с носителем хинтов. Repair покрывает все ключи, включая те, что никто не читает.

## 8. TTL и компакция

```sql
ALTER TABLE user_actions
WITH compaction = {
    'class': 'TimeWindowCompactionStrategy',
    'compaction_window_unit': 'DAYS',
    'compaction_window_size': '1'}
AND default_time_to_live = 2592000;   -- 30 дней
```

TTL-эксперимент сценария `compaction`: 5 строк `USING TTL 5` на месте до истечения, через 8 секунд их 0; чтение истёкшей партиции с `TRACING ON` даёт `Read 0 live rows and 6 tombstone cells` (`results/tracing.txt`), major compaction в `results/compaction.txt`.

> Почему TWCS подходит журналу событий, а STCS нет?

Журнал это поток с монотонным временем и TTL. TWCS раскладывает записи в окна по времени (сутки) и компактирует внутри окна, окна между собой не сливая: остывшее окно с истёкшим TTL удаляется файлом целиком. STCS сливает файлы похожего размера независимо от времени, истёкшие строки перемешиваются с живыми, и для сброса TTL приходится переписывать живые данные.

> Как TTL соотносится с gc_grace_seconds?

`gc_grace_seconds` (864000, 10 суток в 5.0) это срок, который tombstone гарантированно живёт и не сжимается компакцией: окно на доставку факта удаления до всех реплик. TTL-строка по истечении сама становится tombstone, а ещё через gc_grace компакция сбрасывает и данные, и маркер. Правило: периодический repair заметно реже, чем gc_grace.

> Почему TTL предпочтительнее массового DELETE?

DELETE создаёт всплеск tombstone в один момент и требует самому помнить, что и когда удалять. TTL не требует второго запроса: срок едет в строке при записи, каждая реплика вычисляет истечение сама, истечения распределены во времени.
